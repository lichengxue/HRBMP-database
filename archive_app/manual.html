FJS Supabase Uploader: start-to-finish guide

This local app prepares and uploads one photo batch with its matching survey records. Preparation and review happen on your computer. Supabase changes begin only after you enter your private API key and confirm Upload & verify.

1. What to have ready

  • A local copy of HRBMP-database containing archive_app, scripts, docs, and supabase. A GitHub page alone cannot run the GUI.
  • All ZIP parts from one download group, such as Batch5_Named_Photos-…-001.zip, …-002.zip, and …-003.zip, together in Downloads or another local folder. Wait until downloading finishes. Alternatively, provide an existing folder containing sample folders.
  • A local survey CSV: either the full confidential dataset or a subset covering this batch. It needs SAMPLE.NUMBER and collection year or date. Task and date are also checked when available. Keep all species rows for the selected samples.
  • The data dictionary workbook (.xlsx). Obtain the actual workbook separately; the repository's Markdown dictionary is not a replacement for this workbook.
  • The Supabase project URL and a private secret/service-role API key. Enter the key yourself only at Upload. The key is not needed to merge files or prepare and review the package.
  • R, Python, and working disk space. Allow space for the ZIPs, temporary extraction, merged files, and prepared upload copies. Choose a local work folder outside Git, for example C:/Users/your-name/Desktop/FJS_Archive_Work.

2. Get the code and install dependencies once

Download the repository using GitHub's Code → Download ZIP and extract it locally, or clone it with Git. The folder may be named HRBMP-database or HRBMP-database-main. Keep confidential datasets, downloaded photos, ZIPs, API keys, and generated packages outside that folder.

git clone https://github.com/lichengxue/HRBMP-database.git
cd HRBMP-database
Rscript --version
python --version
Rscript --vanilla scripts/install_fjs_archive_app.R
python -m pip install pandas openpyxl

For a downloaded repository ZIP, open PowerShell and change to its extracted folder instead of running git clone. If Rscript is not on PATH, use the full path to your installed Rscript.exe, for example & "C:\Program Files\R\R-4.5.2\bin\Rscript.exe", in place of Rscript. Use your own installed R version.

If Python is not found by the app, set $env:FJS_PYTHON = "C:/path/to/python.exe" before starting it. Install pandas and openpyxl with that same Python executable.

If your original survey is an RDS file, export it to a confidential CSV outside Git before selecting it:

Rscript --vanilla scripts/convert_fjs_rds_to_csv.R "C:/private/survey.rds" "C:/private/survey.csv"

The converter keeps the original RDS, preserves missing values, and pads short sample numbers to four digits. Longer historical identifiers are retained. Excel may hide leading zeros unless you import the column as Text; matching treats 4 and 0004 as the same identifier.

3. Start the GUI

Rscript --vanilla scripts/start_fjs_archive_app.R

The launcher opens your browser. If needed, open http://127.0.0.1:8840/. Keep the PowerShell window open: “Listening on…” means the app is running. Stop it with Ctrl+C. Run locally on this computer.

4. Step 1 — Sample files

  1. Choose Downloaded ZIPs or Sample folders.
  2. For ZIPs, Browse to the folder containing them, choose the download group and correct number of parts, then click Merge files & continue. Do not mix different batches.
  3. For already extracted files, choose the parent folder containing sample folders such as 98_20180701_0004, then continue.
  4. Under Save location, choose your local work folder outside Git. The app combines split parts, verifies saved files, and preserves the original ZIPs. Temporary extraction is cleaned up after processing.

5. Step 2 — Survey data

  1. Select your full local survey CSV or a matching subset. The full source remains in its original location; only matching rows are saved for this batch.
  2. Select the data dictionary .xlsx and enter a descriptive batch name.
  3. Click Prepare & check upload. The app extracts matching rows, prepares permanent upload copies and database CSVs, and performs a dry run. Nothing is uploaded here.

Browse includes Downloads and Desktop shortcuts. CSV selection shows CSV files, dictionary selection shows XLSX files, and folder selection chooses folders. Lists refresh automatically. Click Name, Size, Modified, or Created to sort, and click again to reverse. Modified and Created initially show newest first.

6. Step 3 — Review

  • Check sample and file totals, the sample IDs, and the quality report. A sample–taxon combination is one taxon in one sample; it is not a distinct species count.
  • Review missing PDFs and representative-photo coverage. A photos-only ZIP may have no PDFs. Multiple photo views can belong to one representative group.
  • Photos without a matching survey taxon record remain local and are excluded from upload. Their filenames appear separately in Review. This is informational and does not block continuing. No taxon record is invented to force a match.
  • Use Back or a completed circle in the left sidebar to correct earlier inputs. Changed inputs require preparation and checks again. Later steps remain locked until prerequisites pass.
  • When satisfied, tick the review box and Continue to upload. The API key is still not required.

7. Step 4 — Upload and verify

  1. Check the Supabase project URL. Enter your private secret/service-role key in the masked field. Never put it into source code, Git, a CSV, or chat.
  2. Click Upload & verify and check the confirmation's destination and counts before confirming.
  3. The app updates database tables first, then uploads the selected files to private storage. The bar counts only confirmed successful file uploads, for example 30/613 files uploaded. Excluded photos are omitted from the total. Failures are shown separately.
  4. After all files upload, wait for verification. A full file bar alone does not mean the workflow is complete. The app reads back sample and asset records and checks stored file existence and size.
  5. The completion screen appears only after verification succeeds and a local completion report is saved. Its Download upload report button gives you a readable text copy. The saved report path is also displayed.
  6. Each package has a reports folder outside Git, containing timestamped TXT and JSON reports. They include verification time, the reporting app version, destination, batch and file counts, excluded photos, evidence paths, and the JSON file inventory/checksums. Previous reports are retained. No API key is saved. You can also inspect the fjs-archive Storage bucket and fjs_samples/fjs_assets tables in Supabase.

Keep the app and terminal open until completion. You do not need to push confidential data or prepared files to GitHub to use the uploader.

8. Errors, retries, and resuming

  • 0 samples matched: confirm that the CSV covers this photo batch. A subset for Batch4 may not cover Batch5. Check year, sample number, task, and date; do not fabricate matches.
  • A new file is absent: verify that the download finished, choose Downloads or its actual folder, and check the expected file extension.
  • Dry run failed: open Run details. Resolve missing files, invalid values, or other reported problems and recheck before upload. A dry run does not test your private API key or prove remote write permissions.
  • Upload stopped or failed: some rows or objects may already be saved. Keep the logs and package; check the error before retrying. Replace files already stored at the same paths is an explicit retry option and can overwrite those objects.
  • Verification failed: keep the local originals and package until the destination is checked. The app does not report completion in this case.
  • Restart: the app saves local progress without your API key. An existing prepared package resumes at Review and is checked again. Enter the key again when ready. Back from Upload clears the key and pending confirmation.
  • Run logs, selected subsets, exclusions, completion reports, and packages stay under your local work folder. Keep the reports and their package together for future reference. Reports describe the remote state as of verification, not its availability indefinitely. Photos excluded from one prepared package remain in the original merged folders; their local paths and reasons are recorded in excluded_local_photos.csv.

9. App versions and updates

The header and footer show the GUI version. Version history is in the adjacent tab. The code is maintained in Git; downloaded data and keys are not part of its version history. A local version number does not mean the changes have been committed, tagged, or published to GitHub.

To update: finish or stop any running task, stop Shiny with Ctrl+C, and obtain the updated code. For a Git checkout, inspect git status first, then use git pull --ff-only when appropriate. Preserve local code changes. For a repository ZIP, extract the new code separately. Keep your existing work folder and confidential source files. Install new dependencies if the release requires them, restart the app, and confirm its displayed version.

For maintainers, the single current version is stored in archive_app/VERSION. Use patch for a fix, minor for a compatible feature, and major for a breaking workflow change:

Rscript --vanilla scripts/bump_fjs_app_version.R patch "Describe the fix"
Rscript --vanilla scripts/bump_fjs_app_version.R minor "Describe the feature"

The command updates the version and local release notes together. Review and test the change, then commit those code files through your normal Git workflow. It does not push or publish automatically.
